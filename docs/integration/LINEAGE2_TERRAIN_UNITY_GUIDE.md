# Импорт terrain Lineage 2 в Unity

Гайд для агента, который будет переносить рельеф и покрытия карты из клиента Lineage 2 в Unity. Цель — сохранить игровые координаты, высоты, отверстия и стыки квадратов, затем восстановить текстурные слои. Документ подготовлен 5 октября 2026 года по текущему коду `l2mapconv-public` и документации Unity 6.0.

Наш конвертер уже читает эти данные и строит terrain для просмотра и радарного рендера. **Отдельный экспорт комплекта heightmap и масок для Unity пока не реализован.** Описанные ниже имена файлов и JSON — предлагаемый контракт обмена. Пример C# поясняет импорт высот; в Unity он в рамках этой задачи не компилировался и не запускался.

## Что брать из клиента

Источник — объект `TerrainInfo` из пакета карты и связанные с ним текстуры. Ссылки могут вести в другие пакеты: не предполагать, что вся информация находится непосредственно в `XX_YY.unr` или только в одном `T_XX_YY.utx`.

| Данные | Что содержат | Применение в Unity |
|---|---|---|
| `TerrainMap`, текстура G16 | Беззнаковые 16-битные отсчёты рельефа | Высоты TerrainData или вершины Mesh |
| `Location`, `TerrainScale` | Положение и масштаб исходного terrain | Восстановление игровых XYZ |
| `QuadVisibilityBitmap` | Видимость каждого квадрата сетки | Маска отверстий |
| `EdgeTurnBitmap` | Выбор диагонали двух треугольников в каждом квадрате | Точная геометрия и интерполяция |
| `Layers[].Texture` | Материал или текстура покрытия | TerrainLayer либо собственный материал |
| `Layers[].AlphaMap` | Маска наложения слоя | Веса покрытий либо последовательное смешивание |
| Параметры слоя | Масштаб, смещение, поворот и другие свойства UV | Настройка покрытия в мировых координатах |

Геодата L2J/L2G и Navmesh — продукты для навигации. Для рельефа брать исходный G16: геодата содержит другие поверхности, квантование и собственную политику высот. Здания, мосты, пещеры и этажи переносить отдельными мешами. Одна heightmap не может хранить несколько высот в одном XY.

## Исходная сетка и игровые высоты

Прочитать фактические размеры G16 из текстуры. Частый вариант — 256×256 отсчётов с шагом 128 игровых единиц, но это не правило для всех пакетов. В нашем загрузчике G16 читается как `uint16` little endian, индекс `y * width + x`.

Для обычного terrain с корректным масштабом текущая формула загрузчика:

```text
sx = TerrainScale.x
sy = TerrainScale.y
sz = TerrainScale.z / 256

originX = Location.x - width  * sx / 2
originY = Location.y - height * sy / 2
originZ = Location.z - 32768 * sz

gameX = originX + x * sx
gameY = originY + y * sy
gameZ = originZ + rawG16[y,x] * sz
      = Location.z + (rawG16[y,x] - 32768) * TerrainScale.z / 256
```

Сначала вычислять в `double`, затем переводить в целевой формат. G16 уже содержит смещение относительно 32768; не считать его значениями игровых Z и не применять формулу повторно к уже вычисленным мировым высотам.

Нулевые/повреждённые масштабы требуют отдельной диагностики. В `TerrainInfoActor` есть историческая обработка broken terrain; её нельзя молча распространять на любые неизвестные карты. Экспорт должен сообщать, какой transform был применён.

Номинальное расположение квадрата `rx_ry`:

```text
squareMinX = (rx - 20) * 32768
squareMinY = (ry - 18) * 32768
```

Например, `22_22` номинально начинается в `(65536,131072)`. Это адрес квадрата, а не доказательство положения `TerrainInfo`: наш код сохраняет фактический actor transform. Если origin не совпадает с номинальным, экспортировать его явно и проверять покрытие. Не привязывать геометрию принудительно к имени файла.

## Полный квадрат и стыки

Для 256 исходных отсчётов через 128 единиц последняя своя вершина находится на 32640, а граница квадрата — на 32768. Для полного квадрата с 256 интервалами нужна сетка **257×257**, включающая общий край с соседями.

В согласованной сетке край `x=256` берётся из соседа в направлении +gameX, край `y=256` — из соседа +gameY, угол — из диагонального соседа. **Каждый сосед имеет собственные Location и TerrainScale.** Сначала получить мировую высоту соседа, а не интерпретировать его G16 через параметры владельца.

Если terrain смещён или сетки иначе расположены, выбирать данные по мировому XY и интерполировать по фактическому треугольнику с учётом `EdgeTurnBitmap`. Простая bilinear-интерполяция может описать другую поверхность.

При отсутствии покрытия записывать отсутствие/приближение в отчёт. Наш текущий визуальный загрузчик умеет clamp и считает `clamped_border_samples`; для приёмки бесшовного экспорта ожидается ноль. Дублирование собственной последней строки — приближение, которое нельзя выдавать за подтверждённый соседний край.

Unity 6.0 принимает квадратные heightmap с разрешением 33, 65, 129, 257, 513, 1025, 2049 или 4097. Поэтому 257×257 естественно подходит этому примеру. Увеличение разрешения добавит интерполяцию, а не новые исходные детали. Для другой исходной сетки проверить совместимость либо выбрать Mesh. [TerrainData.heightmapResolution](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TerrainData-heightmapResolution.html).

## Предлагаемый комплект экспорта

Рекомендуемый минимум для каждого terrain: мировые высоты float32, видимость клеток, диагонали и метаданные. Исходный G16 полезно сохранять для проверки формулы. PNG служит удобным обменным/визуальным дополнением, но не должен быть единственным носителем точных данных.

```text
22_22/
  terrain.json
  height_source_g16.raw       исходные W×H, uint16 LE
  height_world_f32.raw        полная сетка (W+1)×(H+1), float32 LE
  surface_present_u8.raw      W×H, 1 = поверхность, 0 = отверстие
  edge_turn_u8.raw            W×H, выбор диагонали 0 или 1
  layers/
    layer_00_mask.png
    layer_01_mask.png
  textures/
    ...                      декодированные текстуры и описания материалов
```

Пример минимальной схемы. Числа и путь клиента здесь демонстрационные; фактические значения экспортёр обязан читать из выбранного клиента.

```json
{
  "schema": "l2-terrain-export-v1",
  "region": "22_22",
  "terrain_id": "package.object",
  "source_client": "D:/line/clients/Salvation140",
  "source_height_size": [256, 256],
  "height_world_size": [257, 257],
  "cell_size_game_xy": [128, 128],
  "origin_game_xy": [65536, 131072],
  "extent_game_xy": [32768, 32768],
  "height_encoding": "float32-le",
  "height_semantics": "absolute-game-z",
  "row_order": "increasing-game-y",
  "column_order": "increasing-game-x",
  "surface_present_encoding": "uint8-0-hole-1-surface",
  "edge_turn_encoding": "uint8-0-or-1",
  "border_policy": "sample-neighbours-in-world-coordinates",
  "clamped_border_samples": 0
}
```

Дополнить схему исходными transform, именами/хешами пакетов и файлов, размерами каждой маски, порядком слоёв, проверенными UV-преобразованиями и списком неполных данных. При нескольких TerrainInfo не выбирать первый молча: дать каждому собственный идентификатор и описание покрытия.

Все RAW хранить построчно с возрастающим gameY и gameX внутри строки. Проверять ожидаемый размер до декодирования. PNG-загрузчик может иметь другие соглашения о начале изображения; ориентацию сверять с RAW и контрольными точками, а не исправлять случайным Flip Vertical.

## Координаты Unity

Предлагаемое соглашение: Unity X соответствует gameX, Unity Y — gameZ, Unity Z — gameY. Один коэффициент `S` применять ко всем расстояниям: terrain, мешам, камере, коллизии и навигации.

```text
unityX = (gameX - anchorX) * S
unityY = (gameZ - anchorZ) * S
unityZ = (gameY - anchorY) * S
```

Anchor — общая игровая точка отсчёта для загружаемой сцены. `S=0.01` можно выбрать как удобный масштаб проекта, но это предложенное соглашение, не проверенное утверждение о физических единицах клиента. Для примера квадрат 32768 будет иметь сторону 327.68 Unity units. Если Unity-проект уже использует другое соглашение, сохранить его и документировать преобразование.

Для готового Mesh перестановка Y/Z меняет знак определителя преобразования. При неизменных исходных индексах проверить и при необходимости обратить winding; нормали и tangent handedness тоже преобразовать. Проще проверить один заведомо горизонтальный треугольник: он должен быть виден сверху с обычным backface culling. Не скрывать ошибку навсегда двусторонним материалом.

## Создание Unity Terrain

Сначала декодировать `height_world_f32.raw`. Для всех связанных tiles выбрать общий вертикальный диапазон игровых высот `[zMin,zMax]`, положительный `S` и один anchor. В диапазон включить соседние крайние отсчёты. Это позволяет одинаково кодировать общие края и не вводить отдельную вертикальную нормализацию для каждого квадрата.

```text
normalizedHeight[y,x] = (worldHeight[y,x] - zMin) / (zMax - zMin)
TerrainData.size = S * (extentX, zMax-zMin, extentY)
Terrain.position = S * (originX-anchorX, zMin-anchorZ, originY-anchorY)
```

`SetHeights` принимает `float[,]` с индексами `[y,x]` и значениями от 0 до 1. [TerrainData.SetHeights](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TerrainData.SetHeights.html).

Иллюстративный фрагмент после чтения файла и проверки метаданных:

```csharp
// worldZ[y,x] уже хранит абсолютные игровые высоты, включая край соседей.
int rows = worldZ.GetLength(0);
int cols = worldZ.GetLength(1);
if (rows != cols || zMax <= zMin || scale <= 0)
    throw new System.ArgumentException("Invalid terrain dimensions or transform");

var data = new TerrainData();
data.heightmapResolution = cols;
if (data.heightmapResolution != cols)
    throw new System.ArgumentException("Unsupported Unity heightmap resolution");
data.size = new Vector3((float)(extentX * scale),
                       (float)((zMax - zMin) * scale),
                       (float)(extentY * scale));

var heights = new float[rows, cols];
for (int y = 0; y < rows; y++)
for (int x = 0; x < cols; x++) {
    double h = (worldZ[y, x] - zMin) / (zMax - zMin);
    if (double.IsNaN(h) || double.IsInfinity(h) || h < 0 || h > 1)
        throw new System.ArgumentException("Height outside declared range");
    heights[y, x] = (float)h;
}
data.SetHeights(0, 0, heights);
var go = Terrain.CreateTerrainGameObject(data);
go.transform.position = new Vector3((float)((originX - anchorX) * scale),
    (float)((zMin - anchorZ) * scale), (float)((originY - anchorY) * scale));
```

Не зажимать ошибочные высоты через Clamp01: это скроет проблему transform или диапазона. При сохранении в проекте создать TerrainData asset обычным Editor-процессом проекта; приведённый фрагмент сам asset не сохраняет.

Если вместо float32 используется производный RAW uint16, экспортировать его общий `zMin/zMax` и определить нормализацию явно, например `u16/65535.0`. Это другое кодирование, чем исходный G16. Оценка его шага по высоте: `(zMax-zMin)/65535` игровых единиц. Не прогонять точные heightmaps через 8-битную текстуру, цветовую гамму или lossy compression.

## Отверстия и диагонали

В текущем загрузчике `QuadVisibilityBitmap=false` означает отсутствие двух треугольников клетки. Предлагаемый `surface_present_u8.raw` сохраняет эту семантику: 1 — поверхность, 0 — отверстие.

Для Unity заполнить `bool[,] surface[y,x]`: `true` означает поверхность, `false` — отверстие, и передать в `SetHoles`. Название метода легко вводит в заблуждение; инвертировать маску не нужно. [TerrainData.SetHoles](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TerrainData.SetHoles.html).

При heightmap 257×257 маска содержит 256×256 клеток: Unity задаёт `holesResolution=heightmapResolution-1`. [Unity TerrainData bindings](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Modules/Terrain/Public/TerrainData.bindings.cs).

Стандартный TerrainData не предоставляет отдельного импорта нашей диагонали для каждой клетки. Для точного совпадения треугольников использовать Mesh с `EdgeTurnBitmap`. Это особенно важно на седловых и крутых участках, где два разбиения одного квадрата дают разные высоты внутри клетки.

Для сетки с вершинами `a=(x,y)`, `b=(x+1,y)`, `c=(x,y+1)`, `d=(x+1,y+1)` текущая визуальная геометрия использует:

```text
edge_turn = 1: (a,b,d), (a,d,c)
edge_turn = 0: (a,b,c), (b,d,c)
```

Затем применить преобразование координат и корректировку winding. Невидимые клетки пропустить. Это схема текущего `territory::build_terrain_mesh`, а не универсальное соглашение любого стороннего экспортёра.

Нативный Unity Terrain подходит для первого визуального переноса. Если требуется совпадение коллизии с исходными треугольниками, оценить Mesh terrain либо отдельный MeshCollider, отключив дублирующий TerrainCollider. Не заявлять точное совпадение коллизии только по совпадению узлов высот.

## Текстурные слои и маски

Сохранить порядок и номера исходных слотов. Маски — данные: импортировать без sRGB, потери разрядности и lossy compression. Цветовые текстуры и материал настраивать отдельно под render pipeline проекта. Для P8-масок сначала применить palette; байт индекса палитры не обязательно является весом.

В нашем текущем визуальном рендере вес слоя читается из красного канала декодированной AlphaMap. Каждый слой последовательно накладывается через source alpha поверх базовой поверхности. Поэтому **нельзя просто нормализовать все исходные AlphaMap как независимые splat-веса**: это меняет результат.

Для простого alpha-over покрытия без иных материалных операций эквивалентные веса можно вывести так, где слой 1 рисуется раньше слоя 2:

```text
wBase = product(1-alpha[j]), j=1..N
w[i]  = alpha[i] * product(1-alpha[j]), j=i+1..N
```

Это математическое преобразование выбранного режима смешивания. Его надо проверить на реальных слоях. Остаточный `wBase` тоже учитывать, например отдельным базовым слоем. Для иных blend-операций или сложных материалов сохранить исходную семантику в shader либо использовать отдельно запечённый цвет покрытия. Радарный PNG может содержать меши и освещение и потому не является автоматически чистой terrain albedo.

Unity `SetAlphamaps` принимает массив `[y,x,layer]`; последний индекс соответствует порядку `terrainLayers`. [TerrainData.SetAlphamaps](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TerrainData.SetAlphamaps.html).

Размеры alpha maps не обязаны равняться heightmap. Переносить маски по их UV и метаданным; отверстия/диагонали пересэмплировать как дискретные данные, не bilinear. Для весов отдельно выбрать и проверить линейную фильтрацию.

Наш `terrain_mapping` подтверждён для ограниченного варианта P542: XY, TerrainScale X/Y=128, нулевые pan/rotation, положительные UScale/VScale и сериализованный layer Scale. Для него:

```text
su = 2 * layer.Scale.x / (128 * 128 * layer.UScale)
sv = 2 * layer.Scale.y / (128 * 128 * layer.VScale)
u  = (gameX - (Location.x-16384)) * su
v  = (gameY - (Location.y-16384)) * sv
```

Не принимать эту формулу за доказанную для Salvation140, другого клиента или rotated/panned слоёв. Предпочтительно получать от экспортёра проверенное world-to-UV преобразование с признаком `verified`. Для простого варианта период покрытия соответствует `1/su` и `1/sv` игровых единиц; при выбранном `S` это кандидат для Unity tileSize, который необходимо сверить контрольными точками. Смещения, повороты и отображение материала могут потребовать custom shader. [TerrainLayer.tileSize](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TerrainLayer-tileSize.html).

Нормали рельефа можно получить из высот или исходного Mesh. Это геометрические нормали; их нельзя выдавать за восстановленную normal map материала. Для текстуры tangent-space normals требуется соответствующий UV/tangent basis.

## Соединение объектов Terrain

Сначала обеспечить совпадение мировых координат и высот общих крайних отсчётов. Затем для каждого Terrain вызвать `SetNeighbors(left, top, right, bottom)`. В выбранной системе:

| Аргумент | Сосед в игровых координатах |
|---|---|
| left | отрицательный gameX |
| top | положительный gameY |
| right | положительный gameX |
| bottom | отрицательный gameY |

Для согласованной сетки номеров это `(rx-1,ry)`, `(rx,ry+1)`, `(rx+1,ry)`, `(rx,ry-1)`. При смещённых terrain проверять фактическое примыкание. У отсутствующего соседа передавать null.

Настроить соседей у каждого объекта. API согласует LOD соседних Terrain, но не исправляет разные исходные высоты краёв. [Terrain.SetNeighbors](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Terrain.SetNeighbors.html).

## Порядок первой проверки

1. Зафиксировать клиент, квадрат, исходные TerrainInfo/Texture references и хеши. Не смешивать 542 и Salvation140 в одном тесте без явного выбора.
2. Получить фактический комплект экспорта. Если его ещё нет, реализовать/заказать экспорт по согласованной схеме; файлов из примера пока не существует.
3. Импортировать один квадрат без покрытий. Проверить оси, origin, размеры, формулу высот и видимость сверху.
4. Добавить отверстия. Проверить настоящий вход в подземелье визуально и коллизией.
5. Подключить соседей +X, +Y и диагональ для проверки сетки 2×2. Измерить расхождение общих краёв и угла.
6. Проверить несколько узлов и точек внутри треугольников: плоскость, склон, седловая клетка, граница, отрицательный Z. Отдельно записать погрешность Unity Terrain и точного Mesh.
7. Включить один текстурный слой, затем остальные в исходном порядке. Сверить хотя бы три контрольные точки по положению масок и масштабу текстуры.
8. Только после этого переносить дополнительные меши и настраивать стриминг сцены/навигацию.

Критерии приёмки: размеры совпадают с metadata; ошибки декодирования или неопознанные transform явные; общие края используют одинаковые мировые отсчёты; маска отверстий не инвертирована; отрицательные высоты сохранены; покрытия не зеркальны; допускаемые погрешности посчитаны и указаны в игровых единицах.

Подъём +24/+32 из L2J не применять к исходному terrain. Исследование Navmesh в Гиране подтверждало другую, CSG-поверхность: оно не является контрольной точкой terrain. Для terrain выбирать точку, где известно, что источником пола служит TerrainInfo.
